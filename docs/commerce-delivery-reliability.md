# 商品交付与启动可靠性

此修复以远端 main `82ab0f6684bbead0980c644afcdd0a0609b19e4f` 为基线，仅涉及商品交付、通知认证和数据库初始化顺序。首页、导航、全局样式、依赖和部署配置保持基线版本。

## 行为约定

- 数据库迁移在 singleton 初始化结束时执行，早于定时任务启动；迁移失败必须阻止启动。
- `/api/notifications/**` 要求有效登录，匿名调用返回认证错误；通知仍按当前用户隔离。
- 普通商品（`NONE`）发布和下单需要非空交付正文。后台草稿仍可暂存不完整配置。商品价格和库存的既有错误优先级保持不变。
- 公开商品接口不返回交付正文；管理员商品接口保留配置内容。
- 发信时再次校验实际交付正文，禁止用商品描述、副标题或通用成功提示冒充交付内容。缺少正文时不请求 SMTP，失败日志以独立事务保留。
- 配置修复后补发成功，只清除该订单准确匹配的“缺少交付内容”错误；保留其他错误或并发更新。

## 独立邮箱库存的交付方式

需要一单分配一个邮箱时，将商品设为 `CDK_EMAIL`，从邮箱接码模块选择该账号所有者持有的未交付主邮箱，并将一条完整 `邮箱----取码链接` 导入商品 CDK。不能把真实库存写入普通商品公共文案。不同子邮箱共用主邮箱时，现有公开取码能力不保证内容隔离，不应当作独立库存出售。

从 `NONE` 转为 `CDK_EMAIL` 后，普通库存字段按既有 API 归零，展示库存改为 AVAILABLE CDK 数量。补发已支付的历史订单沿用原订单，不重复结算或扣减普通库存；无绑定时按照最小 AVAILABLE CDK ID 分配。

补发接口会再次发送已绑定的 CDK，不具备邮件幂等性。发生超时应查询订单、CDK 和邮件日志确认，不自动重复提交。SMTP SUCCESS 说明服务器接收发信请求，真实收件内容仍需单独验收。

## 自动验证

候选验证包括前端 `npm run check`、后端 Maven `package`，以及显式启用的真实回环 HTTP/MySQL/SMTP 协议测试和运行中应用的权限测试。回环 SMTP 使用 `.invalid` 测试内容，不连接公网支付、邮箱或生产数据库。

协议测试需提供通过进程与数据目录核验的隔离 manifest：

```text
./mvnw -B -ntp -Dtest=CommerceProtocolIntegrationTest -Dcommerce.protocol.test.enabled=true -Dcommerce.protocol.test.manifest=<isolated-manifest> test
./mvnw -B -ntp -Dtest=ProductionAuthorizationHttpIT -Dauthorization.fixture-manifest=<running-app-manifest> test
```

运行结果和实际测试数以该候选的报告为准，不能复用其他分支的验收数字。CI 默认不会执行这两项需要隔离夹具的完整验收。

2026-10-15 的候选验证结果：前端 95 项测试、ESLint、TypeScript 和生产构建通过；Maven package 中常规 170 项通过、9 项协议测试按默认条件跳过，随后显式运行的协议 9 项和权限 10 项全部通过。权限测试包含 155 个真实 HTTP 断言，涵盖匿名、USER、ADMIN、OWNER、会话失效及通知归属，7 个临时账号已清理。去重后共 284 项前后端测试实际通过。协议回调使用该基线已有的 `/notify` 路由；不包含后续分支的尾斜杠路由或 Hook 通道。

打包后的完整应用连接本机隔离 MySQL/Redis 达到 health=UP；启动竞态由自动化生命周期回归覆盖，协议数据库按每次运行新建并清理。上述结果均为隔离环境验收，不代表生产部署和真实外网支付、收件已完成。

## 发布与生产验收

推送 main 会触发既有自动生产发布；PR 仅执行检查。上线后需要重新核对运行版本、health、匿名通知状态码及公开商品字段，再确认目标订单收到实际邮箱和取码链接。免费订单验收不代表收费通道扣款或公网支付回调已验证。
